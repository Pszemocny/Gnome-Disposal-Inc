### Assumptions (numbered)
1. The album's data source is `stats.typesEaten`; no new save field. A save from before `typesEaten` existed shows every card locked until the next swallow.
2. "Unlocks on its first swallow" replaces the hole-level half of the legend's `known()` rule (A5); the hint "shows up from level N" stays on the locked card.
3. The day/night cycle, its 240 s length and the hole-level-6 gate stay; the task adds hat glow and the Low switch only.
4. "Hats" = the hat cone and brim. The wizard's staff mini-hat, the king's crown and the Boom fuse bands do not glow.
5. Hat glow is implemented as an emissive term in the existing per-type material (shader patch), so draw calls and triangles do not change.
6. A daily run is a fresh run (money 0, level 1, Backyard), not the player's upgraded save, and it is not persisted: a reload restarts it.
7. The daily date is UTC so every player on Earth gets the same seed on the same calendar day.
8. "Same random spawns" = the factory's output sequence (type, tier, yaw, jitter) from the spawn stream; rain and other events use the global stream.
9. The global `Math.random` override in daily mode makes the map identical (every map call happens in the constructor and `rebuildLand`, before any input).
10. The replay stores the instance matrices that `writeInstances()` wrote (16 floats), so squash, swallow and pop animations replay for free; the live game is untouched because no body, timer or state is read or written during playback.
11. Buffer = the last 600 recorded live frames (10 s at the 60 fps cap; longer at lower fps). Playback runs on real time.
12. Only gnomes and the camera are replayed (spec: "gnome/player positions"); everything else freezes.

### Alternatives rejected
Album:
- (a) a separate "Album" overlay or tab: the spec says "legend card"; the Gnomes tab already is the album, the change is the unlock rule and a counter.
- (b) a hook in `hole.consume` for the discovery toast: `hole.ts` is a hot shared file; polling 12 counters per frame (slowmo's pattern) costs nothing and keeps A to two files.
Day/night:
- (a) a second `InstancedMesh` per type for hats: +12 draw calls and a second matrix write per gnome, against "draw calls unchanged".
- (b) `material.emissive` on the gnome material: emissive is uniform per material and not masked by vertex colour, so the whole gnome would glow; a point light per gnome recompiles every material (CLAUDE "Rules learned the hard way").
Daily:
- (a) switching to daily mode in-process (rebuild the world without a reload): every system keeps run state (hole, events, machines, offline); `?daily` + reload is one line and reuses the whole boot.
- (b) seeding only `rand()`/`pick()` in `context.ts`: `rebuildLand` has a direct `Math.random()` (bushes) and 17 other files call it directly; the global override in daily mode is one line and complete.
Replay:
- (a) a 7-float position+rotation buffer with its own matrix composer (5.4 MB instead of 12.3 MB): loses squash/swallow/pop, needs type/slot bookkeeping and a second writer that must mirror `writeInstances()`.
- (b) Rapier `takeSnapshot()`/`restoreSnapshot()` and re-simulation: gnome AI and the player input are random/non-recorded, so the replay would differ from what the player saw, and restoring the world is not "exactly the live state".

### Ladder
- `album.ts` (rung 6): "every type unlocks on its first swallow ... with a counter"; the toast is the "unlock" the player sees. `legend.ts` edits (rung 2): reuse the existing cards and `.st` class.
- `nightShade` field and the `prefs.quality` compare (rung 2/3): "off on Low quality"; `glow` attribute + `onBeforeCompile` (rung 3, three's own hook): "hats glow a little at night" with "performance unchanged".

### Risks
- Daily: `Math.random` override at module evaluation changes `THREE.MathUtils.generateUUID` output (harmless) and every AI/fx roll (deterministic until the first input). - Album: players with old saves lose the "seen at this level" cards until they feed each type once (decision 1).
- Shared `main.ts`: C edits 4 lines during the run; the orchestrator adds D's 3 lines after D returns; step 0 edits happen before launch. No two editors at the same time.
