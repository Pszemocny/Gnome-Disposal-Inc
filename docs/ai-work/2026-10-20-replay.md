## Problem

Night 2 asks for an instant replay: one key shows the last 10 s of gnome and player motion with the game paused, memory bounded, and then the live game continues exactly where it was.

## Summary

Ladder: `replay.ts` is rung 3 (fixed `Float32Array`/`Uint16Array` ring buffers, allocated once) plus minimum code. The input is what `writeInstances()` already wrote into each type's `instanceMatrix` (rung 2), so squash, swallow and pop replay for free and no second matrix composer exists.

What changed:
- `src/systems/replay.ts` (new): `Replay` with three typed arrays allocated once: matrices `600 x 320 x 16` floats (12,288,000 B), camera `600 x 8` floats (19,200 B: position, quaternion, fov), per-type counts `600 x 12` `Uint16` (14,400 B). Total 12,321,600 B, constant.
  - `record()` runs after `writeInstances()` and `drawCrates()` in the live block: for each type in `GNOME_TYPES` order it copies the first `count x 16` floats of `instanceMatrix` into the ring, at most 320 gnomes per frame in total, then the camera.
  - `update(realDt)` runs every frame before the live block. Paused: stops a running replay and returns. `I` with at least one recorded frame starts it (saves the live per-type `count`, big text "INSTANT REPLAY / I to skip"). While playing: 60 recorded frames per real second, oldest first; the end of the buffer or `I` again stops it.
  - `stop()` (private): restores every mesh `count` and calls `writeInstances()`, which writes the live matrices again from the untouched gnomes. The camera is rewritten by the next `player.update` (live block, or the paused one-frame `player.update(0)`).
- `src/main.ts`: import; `replay.update(realDt)` after `dt`; live block `if (!replay.playing && !ctx.paused)`; `replay.record()` after `drawCrates()`; the paused redraw branch is now `else if (ctx.paused && redraw)`.
- `src/ui/hud.ts`: controls panel, Moving line: `I replay`. (The legend KEYS row came with item A.)

Decisions:
1. First 10 s: with an empty buffer (only possible on the very first live frame, recording starts at the first unpaused frame) `I` does nothing. With 1..599 frames recorded, `I` plays what there is (a shorter replay), as the plan's `size > 0` says. Time on a menu is not recorded, so the replay is the last 10 s of play, not of wall time.
2. Playback speed is 60 recorded frames per real second (plan assumption 11). At less than 60 fps the window covers more than 10 s of play and plays back faster than real time; at the 60 fps cap it is exactly 10 s.
3. Coins, crate, props, robots, particles, HUD numbers, weather freeze (plan decision 16 a)). The player's view-model arm moves with the camera.

Odstępstwa (from the plan's D steps):
- The paused redraw branch had to change: with only the plan's 3 lines, `else if (redraw)` would run `player.update(0)` on every playback frame (redraw is true while unpaused) and overwrite the replayed camera. Now `else if (ctx.paused && redraw)`, same behaviour as before when no replay runs.
- `bytes` counts all three arrays (12,321,600 B), the plan's 12,307,200 left out the 14.4 KB counts array.
- `stop()` is private (only `update()` calls it; a public stop with no replay running would have zeroed the live counts).
- No `context.ts` change: the plan lists none for D, and the scenario reaches the module through the URL the app loaded it from.

Odrzucone:
- Restoring the camera inside `stop()`: the next `player.update` rewrites position, quaternion and fov from the player's own state, so it would be dead code.
- A `ctx.replay` field for tests: the scenario imports the app's module instance, no production line needed.
