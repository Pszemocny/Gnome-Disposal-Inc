## Plan v0 (plan-author)

### Goal
Every error a player hits in the GitHub Pages build (and the game's own `[gnome]` measurement lines) lands as one row in `public.errors` on the leaderboard's Supabase project, at most 20 rows per page load and 2000 per day, readable only from the dashboard, and the game never notices when Supabase is down.

### Data
- New table `public.errors` (`supabase/errors.sql`, applied once through the Management API, token from Keychain `supabase-access-token`, never printed): `id identity`, `created_at timestamptz default now()`, `session text` (36-char uuid check), `build text` (≤ 200), `source text` (check in `error|unhandledrejection|webglcontextlost|note`), `message text` (1..1000), `stack text` (≤ 3000, default ''), `ua text` (≤ 300, default ''), `level smallint null` (1..99), `land smallint null` (0..9), `count integer` (1..1000000, default 1).
- Indexes: `errors_created (created_at)` for the 24 h count; `errors_session (session)` for the per-session count. Trigger `errors_guard` (before insert, security definer, `pg_advisory_xact_lock(hashtext('public.errors_guard'))`, then the two counts), the same shape as `scores_guard` (`leaderboard.sql:30-55`).
- Grants/RLS: `enable row level security`, `revoke all from anon, authenticated`, `grant insert (session, build, source, message, stack, ua, level, land, count) to anon`, one insert policy `with check (true)`, no select policy, no select grant. `Prefer: return=minimal` needs no select right (return=representation would).
- Volume: `public.errors` starts at 0 rows; `public.scores` was 0 after cleanup on 2026-10-21 (`2026-10-20-supabase-leaderboard.md:73`, not re-queried: no reading prod without PP's word). Row size ≤ ~4.6 KB (1000 + 3000 + 300 chars + fields). Honest play: ≤ 20 rows per page load. Flood at the cap: 2000 rows/day ≤ 9.2 MB/day, so a non-stop flood needs ≥ 54 days to fill the 500 MB Free database; cleanup = delete rows in the dashboard. Cost per insert: 1 lock + 2 index-range counts (≤ 2000 and ≤ 20 entries). Browser cost: at most 20 `fetch` calls per page load, each ≤ 5 KB, `keepalive` quota 64 KB in flight (20 × 5 KB may exceed it only if all 20 fire in the same instant; each has its own 3 s window, accepted).

### Assumptions (numbered)
1. "Dedupe + counter" means: one row per distinct message per page load, `count` = occurrences within the first 3 s (or until `pagehide`); later repeats are counted only in the on-screen box. Inserts cannot be updated with the public key, so a running counter would need extra rows.
2. "Browser/OS from the user agent" = the raw `navigator.userAgent` string trimmed to 300 chars; PP reads the browser/OS off it in the dashboard. No parsing code.
3. "Time" = server `created_at` (the leaderboard learned that the browser clock is unreliable: `fix-plan-supabase-leaderboard-r1.md` F4).
4. "Build version (hash)" = the existing `BUILD` (`crash.ts:4`, `assets/index-<hash>.js` on Pages).
5. "Daily global cap like the leaderboard" = 2000 rows per 24 h with the same advisory-lock trigger shape; plus a server-side per-session cap of 20 because the client cap is skippable by a script.
6. The errors sink switches on under the same condition as the online board (all three variables + publishable key), although it does not use the salt: one switch, one README rule.
7. Supabase's own API logs keep request metadata (IP) on their side for their retention period; this is outside the game's control and unchanged by this plan.
8. `crypto.randomUUID()` exists wherever the sink runs: Pages is https and the `vite preview` test on `127.0.0.1` is a secure context; on plain http LAN (5300) the sink is never created (row 2).

### Alternatives rejected
- (a) Reuse `navigator.sendBeacon` for Supabase: a beacon cannot carry the `apikey` header; `fetch` with `keepalive: true` is the platform equivalent that can.
- (b) A separate module `src/ui/errors.ts`: `crash.ts` already owns capture, the box and the beacon; the sink is ~40 lines in the same file (ladder rung 2 over a new file).
- (c) Pass the config from `main.ts` into `installCrashReport()`: `main.ts` is in flight for the factory packages; `crash.ts` reading `online` from `leaderboard.ts` keeps `main.ts` untouched.
- (d) Send every repeat as a row or a second "final count" row on `pagehide`: more rows and a confusing `max(count)` query for PP; rejected for the 3 s window.
- (e) An offline queue in localStorage with retry on the next load: not asked; a dropped row when Supabase is down is accepted (spec: the game keeps running).
- (f) A per-minute global cap (like 30/min per board): a real crash wave on a broken build would lose rows exactly when PP needs them; the 24 h cap and the per-session cap bound storage.
- (g) Retention/auto-delete of old rows: not asked; PP deletes in the dashboard.
- (h) Parsing the UA into browser/OS columns: ~20 lines of brittle regex; the raw string answers the same question.
- (i) Reading the user agent server-side from `request.headers` in the trigger: avoids one client field but adds PostgREST-specific GUC code; one client line wins.

### Chosen variant
A write-only sink inside `crash.ts`, fed by the three capture paths and `note()`, deduped by message with a 3 s counting window, flushed on `pagehide`, posting through the leaderboard's lifted `restCall` only when the board is online; a separate `public.errors` table with a `security definer` trigger (one advisory lock, per-session cap 20, per-class cap 2000/24 h), insert grant on named columns and no select; `build` carries the commit SHA; README gives PP one group-by query that lists distinct bugs without the measurement noise. Pros: nothing new to configure (same three variables, same key guard), the game cannot be broken by the sink (every send is fire-and-forget in try/catch, `flush` is a no-op on a missing entry), a per-frame error loop shows as one row with `count` ~180, measurements cannot close the error log, stacks map to a commit. Cons: ~45 lines in `crash.ts` for the window/flush logic; errors in the last 3 s before a tab is killed without `pagehide` (mobile Safari) are lost; a script with the public key can still fill a day's budget. Cost (performance): ≤ 20 `fetch` per page load, each ≤ ~5 KB; per insert 1 lock + 2 indexed counts (≤ 4000 keys on `created_at`, ≤ 21 on `session`); storage ≤ 18.4 MB/day at both caps (two budgets of 2000 × ≤ 4.6 KB), ≥ 27 days of non-stop flood to fill the 500 MB Free database, cleanup = delete rows. Risk (roast): flood closes reporting for 24 h (accepted, same as the board); adblocker makes those players invisible (accepted, revisit criterion above); keepalive + preflight during unload unverified until step 8 (pinned there). Ladder: rung 2 for `restCall`/`online`/trigger shape/`check.sh` helpers/`ctx.state` fields, rung 3 for `fetch keepalive`, `pagehide`, `crypto.randomUUID`, `navigator.userAgent`, Vite `define`, rung 6 for `queue`/`pending`/`seen`/`rows` and the scenario; no new dependency.

### Rejected variant(s)
- (b) Immediate send, no counter: on the first occurrence of a message POST at once with `count = 1`; no `pending`, no timers, no `flushAll`, no `pagehide`, no keepalive. Pros: ~20 lines less, removes the flush-after-flushAll class and the unload/preflight question entirely. Cons: a per-frame error loop (the exact class in CLAUDE.md "do not touch a removed gnome's body again") looks identical to a one-off glitch (`count` 1 in both), so PP cannot tell "the game froze and looped" from "one hiccup"; the hub's spec asks for "dedupe per session + counter". Rejected because of that scenario; it stays as Q3 option b for PP.
- (c) `source`-specific tables or a `notes` table: Pros: PP's Table Editor view is clean without a query. Cons: two tables, two triggers, two grants, two check blocks for one line of `where source <> 'note'`. Rejected because the query gives the same view at zero schema cost.
