# Animation options: why the game feels wooden and what to use (2026-10-20)

Research only, no code change. PP (via hub): "poszukać jakiejś biblioteki animacji do tego albo serwera MCP, bo to bardzo drewniane jest".

## Problem

Gnomes, robots and tools move stiffly. PP asked for an animation library or an MCP server. Before picking a tool we need to know what in the code makes it look wooden, and which tool actually fixes that on this stack (three 0.186, Rapier, instanced primitives, no downloaded models).

## Summary

### Why it looks wooden (from the code)

1. **One rigid block per gnome.** `src/world/models.ts:5` ("Every model is a merge of coloured primitives, so one mesh = one draw call") and `gnomeGeometry()` (`models.ts:51-101`) bake legs, arms, beard, hat and head into one buffer. `src/entities/gnomes.ts:110` draws each type as one `InstancedMesh`, and `writeInstances` (`gnomes.ts:772`) writes one matrix per gnome. No part can move relative to another, so nothing can swing, nod or wobble. This is the root cause; every other point below is a symptom of it.
2. **Walk = whole-body hop.** `gnomes.ts:734-744`: the walk pose is `|sin| * 0.05` bob, `sin * 0.08` roll and a fixed `0.12` lean. The gnome slides along the ground as a statue that hops 5 cm. Rule 10 is met on paper (the pose follows `linvel`), but with no legs stepping and no arms counter-swinging it reads as sliding.
3. **No secondary motion.** Nothing lags behind the body: beard, hat and arms are fixed to the torso (same cause as 1). The lean is set directly from the current velocity (`gnomes.ts:743`, no damp), so a direction change snaps the lean in one frame. The turn uses `g.yaw += angleDiff(...) * Math.min(1, dt * 8)` (`gnomes.ts:510`), the pattern rule 1 forbids, and five more such lines exist (`environment.ts:439,449`, `events.ts:318`, `coins.ts:199`, `sweeper.ts:166`).
4. **Statue, ragdoll and held gnomes are dead weight.** `writeInstances` (`gnomes.ts:734-771`) only adds motion for `walk`, `falling`, `squash`, `pop` and `held`. A statue has no idle (no breathing, no look-around). A ragdoll is a rigid capsule tumbling from physics, so a thrown gnome flies like a bowling pin, limbs frozen. The `held` wiggle is a fixed-frequency `Math.sin(ctx.time * 16)` (`gnomes.ts:770`), so every held gnome shakes in the same mechanical rhythm.
5. **Machines and robots spin and slide at constant speed.** `machines.ts:711` (fan `+= dt * 25`), `:760` (wheel `+= dt * 7`), `:828` (vacuum/blackhole), `factory.ts:179`, `mushrooms.ts:88`, `events.ts:294,298` all use `rotation += dt * CONST` with no spin-up or spin-down (rule 7). Robots (`robots.ts:88-104`) are a truck mesh plus a bed: the bed tilts with eased curves (`robots.ts:613-616, 646-649`), but there are no wheels turning, no suspension bob, no lean into turns, so the truck glides like a chess piece.

What is already fine: timed one-shot effects (pop, squash, kick leg, throw recoil, cannon recoil, swallow) use `src/core/ease.ts` with three phases where it matters. Timings are not the problem; structure is.

### Recommendation

Option 1, procedural animation on per-part instances, with `BatchedMesh` so draw calls stay at today's count. It fixes all five causes, adds no dependency, no asset and no licence, keeps the primitive look PP has, and costs 2-3 days. Skeletal animation (option 2) is the "real" answer for a game with downloaded characters, but here it means either breaking the no-asset rule or hand-rigging primitives, plus a fragile instancing workaround, for 5-8 days. A tween library (option 3) and MCP servers (option 4) do not move a single limb; they are not the missing piece.

Rejected: GSAP/Motion as a dependency (the ladder: `ease.ts` + bundled Tween.js cover timed curves). theatre.js (no commits since 2024-08, studio is AGPL). VAT (needs Blender bakes per type, 3-star runtime). Blender MCP / three.js devtools MCP (not added to any config; useful only after a switch to rigged assets, and they execute code on PP's machine).

### Demo to build next (one task)

Scope: the `classic` gnome type only, walk and idle, nothing else moves yet.

1. `models.ts`: `gnomeParts(t)` returns the parts split into: torso (pants, belt, shirt, head, nose, eyes, extras), hat (cone + brim), beard, left arm (cylinder + hand), right arm, left leg, right leg. Each part keeps its own pivot at the joint (shoulder, hip, chin, hat brim) so a rotation swings it.
2. `gnomes.ts`: for the demo type, one `BatchedMesh` with 7 geometries and `capacity x 7` instances; `writeInstances` composes 7 matrices per gnome from the body pose: legs swing `sin(ph)` and `-sin(ph)` around the hip (amplitude 0.6 rad x speed ratio), arms counter-swing at half amplitude, beard and hat follow the torso through a spring (`damp` of the pitch toward the lean, lambda 12, plus a vertical lag on each step), torso bob stays as today but on `|sin|` with `outCubic`. Idle (zero velocity): a 0.5 Hz breath on the torso scale y (±1.5 %), hat tilt noise from `SimplexNoise` (already imported in `fx.ts`), one head turn every 3-6 s with `outBack`.
3. Side by side: a scenario spawns two `classic` gnomes 1 m apart walking the same path, one drawn by the old single-matrix path (flag on the gnome), one by the part path; screenshot both at the same frame.
4. Check (rule 12): the headless scenario samples the left-leg matrix over >= 40 frames and asserts the hip angle crosses zero at least 4 times with peaks within ±0.6 rad, the hat pitch lags the torso lean by 2-6 frames after a direction change, and the beard pitch overshoots the torso pitch at least once per direction change. Draw calls in `renderer.info` stay <= today's count + 1 for the demo type. A standing gnome's leg matrix does not change. Screenshot at the frame of the largest leg angle, checked by eye against the old gnome next to it.
5. Done when PP sees the two gnomes and says which one to keep; if the new one wins, the same split goes to the other 10 types, then ragdoll flail, held kicking, statue idle and robot wheels/suspension, each with its own scenario.
